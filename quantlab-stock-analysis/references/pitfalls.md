# 已验证的坑

这份清单是实际踩过、并且用真实数据或代码验证过的。给出任何结论前扫一眼，判断哪些会影响到这次的分析。

## 一、数据本身

**1. 未复权。** `bars` 存的是原始价。除权除息日会出现假暴跌：`(CLOSE-REF(CLOSE,1))/REF(CLOSE,1)` 当天可能是 -30%。跨除权日的均线、布林带、涨跌幅指标都会带上台阶。要用到跨除权的长周期指标时，先在结论里注明，或只用除权日之后的窗口。

**2. 停牌和无成交是占位 K 线。** 库里约 3% 的行 `volume = 0`（实测 479057 行／1710 万行），这些行 `amount` 也是 0，价格沿用前收。后果：均量类指标被拉低、涨跌幅算成 0 后被计入"持平"、`VOLUME>MA(VOLUME,20)` 这类条件会给出误导信号。算均量/量比/换手时先 `volume > 0`。

**3. 早期数据缺成交额。** 90 年代初很多行 `volume`/`amount` 为 0，用"成交额"类因子做长周期研究时，样本前段基本不可用。

**4. 股票池是"当前上市列表"，存在生存偏差。** 库里的股票来自同步时的在市列表，期间退市的股票不在其中。用它做多年回测，结果天然偏乐观——这是所有"用当下成分股回测历史"的通病，不是本系统的 bug，但结论里要写出来。

**5. 数据截至时间。** 库的最后一根不一定是"今天"，看 `/api/db/health` 的 `last_date`。别把最后一天的数据当成实时行情。

## 二、方法本身

**6. 量纲不可比（最容易犯）。** 价格（元）、成交量（手）、成交额（元）、RSI（0~100）混着比较或求交叉，结果就是噪声。实测对照（同样 300 只股票、同一份数据）：

- `CROSSDOWN(EMA(CLOSE,3), 布林下轨30)` → 事件后 5 日上涨概率 **58.3%**，均值 +1.38%
- `CROSSDOWN(RSI(CLOSE,3), 布林下轨30)` → 事件后 3 日上涨概率 **50.5%**，均值 +0.20%（纯噪声）

想比较"位置"和"强弱"，先把两边都换算成同量纲，例如 `CLOSE/MA(CLOSE,20)*100-100`。

**7. `MID` / `INSIDE` 用了未来信息。** 它们要知道"下一次 b 什么时候出现"，回测会偏乐观。做研究可以，做回测必须说明。

**8. `PEAK` / `TROUGH` 是滞后确认。** `PEAK(s,n,k)` 说的是"k 根前那一根是峰值"，信号出现在峰值之后 k 根，别当成实时信号直接下单。

**9. `ISMAX/ISMIN` 允许相等，`NEWHIGH/NEWLOW` 不允许。** 要"平了也算区间最高"用前者，要"真突破"用后者，选错了命中数会差很多。

**10. 缺失值在逻辑运算里的行为不直观（两个引擎还不一致）。** 比较运算遇到缺失一律返回 0（不成立），但 `NOT` 会把缺失当成"成立"。实测：

```text
NOT(CLOSE>REF(CLOSE,1))   →  [1, 0, 1, ...]   第一根因为没有昨收，"非上涨"= 真
```

更细的差异：把**数值序列**（如 `MA(CLOSE,5)`）直接当逻辑量做 `AND`/`OR` 时，Python 引擎把 NaN 当"真"、JS 引擎把 NaN 当"假"，两边结果不同（实测 `MA(CLOSE,5) AND 1`：Python 得到全 1，JS 得到前面的 0）。正常写法（比较、`CROSS`、`EVERY` 的结果参与 and/or）两边完全一致，所以**不要把数值序列直接塞进 AND/OR**，要用比较表达式。

**11. `warmup` 不够会让前段没有信号。** 均线类指标在预热不足时是 NaN，条件自然不成立。回测默认 `warmup=250`，`/api/screen` 默认 260，别为了"多取点数据"把它调小。

**12. 事件样本不独立。** 同一只股票连续几天满足条件会算成多个事件，`n` 因此虚高。连续型事件（比如"在布林下轨以下"）尤其严重，这类情况更适合用"首次触发"或加冷却期来定义事件。

**13. 反复用同一段数据调参 = 过拟合。** 换手数、换区间、换股票池再验一遍；本系统里换 `days`（242 / 726 / 1210）和 `sample` 就能快速做这种稳健性检查。

## 三、回测口径

**14. 全市场扫描的 `total_return` 是等权累加，不是组合收益。** 它是"每只股票各投一份钱，把各自收益率相加"，用来看策略平均表现，**不能**当作一个账户的资金曲线，也不能直接和买入持有比较——要和 `avg_benchmark`（等额买入持有的平均收益）对比。

**15. `success_rate` 的分母是"有成交的股票"（`traded`），不是全部股票。** 一个只在少数股票上触发、但触发后都赚钱的策略，成功率会很好看，要同时看 `participation` 和 `traded`。

**16. 没有滑点、不检查涨跌停能否成交，手续费只按单边费率收。** 信号落在连续涨停板上一字开盘时，回测假设你买得到，实盘买不到 —— 这类策略的回测收益会系统性偏高。默认费率万三，也不含印花税和过户费。

**17. 部分卖出时 `trades` 只统计回到空仓的完整回合。** 分批建仓/分批止盈的策略，`trades` 会比 `fills` 少很多，看胜率时要注意分母是什么。

**18. 剔除 ST 默认开。** ST 股涨跌幅限制不同（5%），退市风险也不一样；如果研究目标本身就包含 ST，需要显式关掉（`excludeST:false`）并在结论里说明。

## 四、工程与性能（改代码时会遇到）

**19. `SELECT MIN(date), MAX(date) FROM bars` 会全索引扫描。** 1700 万行实测 1.27 秒；拆成两个 `ORDER BY date LIMIT 1` 子查询是 0 毫秒。`market_api.py` 里的 `DATE_SPAN_SQL` 就是干这个的，别改回去。

**20. `bars(date)` 索引是性能命脉。** 没有 `idx_bars_date` 时，按日期查全市场要 1~3.5 秒，建完 30 毫秒。换库/重建库后记得补。

**21. 两个引擎必须同步改。** `expr.py`（服务端筛选/回测/统计）和 `static/whiteboard.js`（页面画线与前端回测）语义必须一致，改一边就要改另一边并逐元素比对（历史记录：70 条表达式 0 差异）。

**22. 实测耗时（本机，供估算）。** 全市场回测扫描 1 年区间 4924 只 ≈ **9.6 秒**；事件统计 300 只抽样 ≈ **10 秒**；`/api/db` 常规查询 2~5 毫秒，全市场截面 70 毫秒，区间排行 ~1 秒。先 `sample` 后全量。

**23. 同步行情时查库可能短暂报锁。** 同步是独立写连接，页面查询会拿到 `database is locked`（已设 8 秒 busy_timeout）。重试即可，不要在这时候做全市场跑批。

**24. 周期参数必须是 1~1000 的整数**，写成 0、负数、小数或超过 1000 会直接抛错而不是静默降级。
